## 正文台词

### 一、开场 · 项目概述

各位老师好。我汇报 **《模拟空战》联机模式**。

本项目是一个**前后端分离的实时对战游戏**。相比单机版在浏览器内完成全部推演，联机版将**权威计算迁移到后端 Spring Boot**，多个客户端通过 **WebSocket** 连接同一房间，以后端 **120 tick/s** 的节奏同步战场。

下面我从**技术栈 → 启动演示 → 联机流程 → 分层架构 → 接口协议 → 数据库与 MyBatis → 并发模型 → 游戏机制**依次介绍。核心代码集中在后端 [**OnlineGameService.java**](air-combat-backend/src/main/java/com/aircombat/service/OnlineGameService.java) 的 **`tick` 方法（约第 349–608 行）** 和前端 [**OnlineGameController.ts**](air-combat-frontend/src/controllers/OnlineGameController.ts)。

---

### 二、技术栈总览

先整体看一下用到的技术：

**前端**方面：
- **Vue 3** 作为 UI 框架，配合 **Vite** 构建打包，纯 **TypeScript** 编写
- 游戏画面用 **Canvas 2D** 渲染，采用了离屏缓冲和脏矩形策略来减少重绘开销
- 状态管理使用 Vue 3 的 `ref` 和 `shallowRef`，没有引入 Pinia 之类的外部库，足够简洁

**后端**方面：
- **Spring Boot 3** 作为整体框架，Java 17 编写
- **REST API** 处理账号注册登录、房间增删改查
- **WebSocket** 处理实时对战通信，路径为 `/ws/game`
- **JWT**（jjwt 库）做登录鉴权，配合 `auth_revision` 字段实现单点登录互踢
- **Spring Security Crypto**（BCrypt）加密密码

**持久化**方面：
- **MyBatis** 作为 ORM 框架，通过 Mapper 接口 + XML 将 Java 对象映射到数据库
- **MySQL** 作为存储引擎，库名 `air_combat`，共 5 张表

**并发**方面：
- `ScheduledExecutorService` 单线程守护，按 120Hz 触发 tick
- 两个 `ThreadPoolTaskExecutor`：`gameTaskExecutor` 执行房间步进、`calculationTaskExecutor` 异步处理 AI 与碰撞

以上技术栈中，**Spring Boot 3 + MyBatis + MySQL + WebSocket** 构成后端骨架；**Vue 3 + TypeScript + Vite + Canvas 2D** 构成前端骨架。

### 三、启动与操作演示

**后端**：先看 [**application.yml**](air-combat-backend/src/main/resources/application.yml)（整体 29 行），配置了 **tick-rate 120**、JWT secret、MySQL JDBC 连接。启动命令 `.\mvnw.cmd spring-boot:run`，终端可见 Spring Boot 启动和 WebSocket 注册。我访问 `GET /api/health` 做健康检查。

**数据库**：启动时 [**schema.sql**](air-combat-backend/src/main/resources/schema.sql) 自动建表（第 1–59 行），共 5 张表——`users`、`rooms`、`room_players`、`battle_records`、`battle_player_results`，后面我会具体讲。

**前端**：`npm run dev` 启动 Vite 开发服务器，默认 `http://localhost:5173`。登录页支持填写后端地址，方便局域网多设备联机。前端通过 [**authApi.ts**](air-combat-frontend/src/api/authApi.ts) 调用 REST 接口完成注册登录，获取 JWT 后存入 [**authStore.ts**](air-combat-frontend/src/stores/authStore.ts)，后续请求在 `X-Token` 头携带。

**双人对战演示**：我预先开了两个窗口——

- 窗口 A 创建房间 → 窗口 B 加入同一房间，选**不同队伍**（RED vs BLUE）
- 房间内可以选机型：J-20、J-16、J-10C、J-25（配置见 [**battlefieldConfig.ts**](air-combat-frontend/src/shared/battlefieldConfig.ts)），每种机型速度、血量、导弹伤害、炸弹伤害都不同。大厅每 3 秒自动轮询刷新，房间列表只展示 WAITING 和 RUNNING 状态
- 房主点击"开始对局"→ 后端 [**OnlineGameService.java**](air-combat-backend/src/main/java/com/aircombat/service/OnlineGameService.java) 的 **`announceCountdownAndScheduleBattle`** 方法（第 312–315 行）广播 `MATCH_COUNTDOWN`，前端全员看到全屏倒计时蒙层 3 秒 → 到点广播 `BATTLE_STARTED`，自动进入战场

进入战场后操作和单机一致：**WASD / 方向键**移动；**鼠标**控制机头朝向；**J / 空格 / 左键**发射导弹；**K / 右键**投弹。HUD 显示实时 FPS 和红蓝存活架数。一方全灭后广播 `BATTLE_FINISHED`，战报入 MySQL。

### 四、前端技术详解

前端虽然是联机模式，但依然保持了 **MVC 分层**（和单机一脉相承）：

- **View 层**：[**OnlineGameView.vue**](air-combat-frontend/src/views/OnlineGameView.vue) 组装画布和 HUD 组件，设置 `continuousRafRender`（联机模式特有——快照未到时仍按显示器刷新率重绘最后一帧，上限 120 FPS）；[**BattleCanvas.vue**](air-combat-frontend/src/components/BattleCanvas.vue) 挂载 Canvas 并创建 [**GameRenderer.ts**](air-combat-frontend/src/rendering/GameRenderer.ts)；[**LoginView.vue**](air-combat-frontend/src/views/LoginView.vue) 和 [**RoomView.vue**](air-combat-frontend/src/views/RoomView.vue) 处理登录和房间 UI
- **Controller 层**：[**OnlineGameController.ts**](air-combat-frontend/src/controllers/OnlineGameController.ts) 负责 WebSocket 建立/断开、每帧发送 `MSG_PLAYER_INPUT`（来自 [**InputController.ts**](air-combat-frontend/src/controllers/InputController.ts) 的键鼠采样）、接收 `BattleSnapshot` 后调用 [**normalizeBattleSnapshot.ts**](air-combat-frontend/src/controllers/normalizeBattleSnapshot.ts) 规范化后再派发给 View
- **Model 层**：[**interfaces.ts**](air-combat-frontend/src/game/interfaces.ts) 定义六大接口；[**types.ts**](air-combat-frontend/src/game/types.ts) 定义 `MessageType` 枚举和消息数据结构

**渲染层面**：Canvas 2D 用了三个离屏缓冲——`worldBuffer`（主画面）、`minimapBuffer`（小地图）、以及 HUD 条带脏区域，避免全画布重绘。机体外形在 [**fighterShapes.ts**](air-combat-frontend/src/rendering/fighterShapes.ts) 中用 Path2D 预生成并缓存。

**状态管理**：[**authStore.ts**](air-combat-frontend/src/stores/authStore.ts) 和 [**roomStore.ts**](air-combat-frontend/src/stores/roomStore.ts) 用 Vue 3 的 `ref`/`shallowRef` 而不是 Pinia，因为状态结构简单，不需要外部依赖。

### 五、后端技术详解

后端按 **Display → Service → Model** 分层：

**Display 层**：
- [**AuthController.java**](air-combat-backend/src/main/java/com/aircombat/controller/AuthController.java)：`/api/auth/register`、`login`、`logout`（含 `sendBeacon` 注销）
- [**RoomController.java**](air-combat-backend/src/main/java/com/aircombat/controller/RoomController.java)：房间 CRUD + 选队/选机型/开始。其中 `startRoom` 调用 `announceCountdownAndScheduleBattle`，先广播倒计时再延迟 3 秒真正开局
- [**GameWebSocketHandler.java**](air-combat-backend/src/main/java/com/aircombat/display/GameWebSocketHandler.java)（第 27–62 行）：解析 `?token=xxx&roomId=xxx` 查询参数，交给 `OnlineGameService.connect()`

**Service 层**（核心）：
- [**AuthService.java**](air-combat-backend/src/main/java/com/aircombat/service/AuthService.java)：使用 **jjwt** 库签发/校验 JWT，`login` 时递增 `auth_revision` 使旧 token 失效（第 68–86 行）；WebSocket 中每 20 条消息或 2s 节流校验一次 `sessionReauthStillValid`，不匹配则关闭连接（4001），实现单点登录互踢
- [**RoomService.java**](air-combat-backend/src/main/java/com/aircombat/service/RoomService.java)：房间逻辑——`createRoom`、`joinRoom`、`selectTeam`、`leaveRoom`。房主 leave 会 `disbandRoom` 踢出全部 WebSocket；每队上限由 `application.yml` 的 `max-team-size: 4` 控制
- [**OnlineGameService.java**](air-combat-backend/src/main/java/com/aircombat/service/OnlineGameService.java)：全项目最大文件（1584 行），核心是 **`tick` 方法**（第 349–608 行），每 tick 在 `synchronized(runtime)` 内串行推进 11 步（后面详述）

**Model 层**：
- 所有游戏状态都用 **Java record** 表示——[**BattleSnapshot.java**](air-combat-backend/src/main/java/com/aircombat/game/BattleSnapshot.java)、[**InputCommand.java**](air-combat-backend/src/main/java/com/aircombat/game/InputCommand.java)、[**FighterState.java**](air-combat-backend/src/main/java/com/aircombat/game/FighterState.java)、[**MissileState.java**](air-combat-backend/src/main/java/com/aircombat/game/MissileState.java)、[**BombState.java**](air-combat-backend/src/main/java/com/aircombat/game/BombState.java)。Record 是不可变的，天然适合作为网络传输的快照载体

**运行时内部类**：`OnlineGameService` 内部定义了 `FighterRuntime`、`MissileRuntime`、`BombRuntime`、`RoomRuntime` 等 `private static final class`，这些是可变运行时对象，只在服务端内存中读写，不直接序列化下发。

### 六、接口先行与协议设计

按照任务书"接口先行"的要求，六大接口在前端 [**interfaces.ts**](air-combat-frontend/src/game/interfaces.ts) 和后端 `com.aircombat.game` 包中各自定义：

| 接口 | 职责 |
|------|------|
| `IFighter` | 战机的移动、武器发射、伤害、状态导出 |
| `IMissile` | 导弹的发射、追踪、失效、状态导出 |
| `IRadarSystem` | AWACS 雷达探测——扫描敌方、输出方位标记 |
| `ICombatJudger` | 碰撞粗筛与精判、战果统计 |
| `IAIController` | 敌方 AI 的决策生成（产生 `InputCommand`） |
| `INetworkProtocol` | 消息的序列化与反序列化抽象 |

**协议实现**：`JsonNetworkProtocol`（前端 [**JsonNetworkProtocol.ts**](air-combat-frontend/src/game/JsonNetworkProtocol.ts)，后端 [**JsonNetworkProtocol.java**](air-combat-backend/src/main/java/com/aircombat/game/JsonNetworkProtocol.java)）负责 `serialize` / `deserialize` / `getMessageType`。选 JSON 的原因是：可读易调试、与 WebSocket 文本帧天然兼容、TypeScript 和 Java 都有成熟的 JSON 库。如果将来需要压缩带宽，只需要换一个 `INetworkProtocol` 实现（比如二进制），不影响上层逻辑。

**消息类型**（[**MessageType.java**](air-combat-backend/src/main/java/com/aircombat/game/MessageType.java) 第 3–11 行，7 种）：

- **上行**（客户端 → 服务端）：`MSG_PLAYER_INPUT`，携带 `InputCommand{moveX, moveY, fire, fireBomb, targetId, fireHeading, fireBombHeading}`。其中 `fireHeading` 和 `fireBombHeading` 是鼠标朝向的世界坐标角度，确保网络传输中发射方向不丢失
- **下行**（服务端 → 客户端）：`MSG_BATTLE_STATUS`（每 tick 广播 `BattleSnapshot`）、`MSG_MISSILE_LAUNCH`（导弹发射事件）、`MSG_HIT_RESULT`（命中结果）、`MSG_ROOM_EVENT`（房间生命周期事件——`PLAYER_ONLINE/OFFLINE`、`MATCH_COUNTDOWN`、`BATTLE_STARTED`、`BATTLE_FINISHED`、`ROOM_EXPIRED`）、`MSG_ERROR`

每条消息包裹在 `NetworkMessage<T>` 通用信封中，包含 `type`、`roomId`、`tick`、`timestamp`、`payload` 五个字段。

**WebSocket 连接关闭码**（4000+ 私有范围）：
- `4000` = `SESSION_REPLACED`：同一 (roomId, userId) 的新 WebSocket 替换了旧连接，旧连接被关闭
- `4001` = `AUTH_REVOKED`：`auth_revision` 被新登录递增，当前 JWT 失效，连接被踢

### 七、数据库与 MyBatis 持久化

**数据库设计**（[**schema.sql**](air-combat-backend/src/main/resources/schema.sql) 第 1–59 行，5 张表）：

| 表名 | 关键字段 | 职责 |
|------|----------|------|
| `users` | `id`、`username`(UK)、`password_hash`(BCrypt)、`nickname`、**`auth_revision`** | 用户账号，`auth_revision` 每次登录 +1 实现单点互踢 |
| `rooms` | `id`、`name`、`owner_user_id`、`status`(WAITING/RUNNING/EXPIRED)、`red_count`、`blue_count` | 房间信息与状态流转 |
| `room_players` | `id`、`room_id`(FK)、`user_id`(FK)、`team`(RED/BLUE)、`fighter_id` | 房间-玩家映射，(room_id, user_id) 联合唯一 |
| `battle_records` | `id`、`room_id`(FK)、`mode`(ONLINE)、`winner`、`duration_seconds`、`red_kills`、`blue_kills`、`report_json`(LONGTEXT) | 对局战报，`report_json` 存储完整快照 JSON 用于复盘 |
| `battle_player_results` | `id`、`battle_record_id`(FK)、`user_id`、`nickname`、`team`、`fighter_model`、`kills`、`damage_dealt` | 每位玩家的对局明细（击杀数、伤害量） |

**MyBatis 映射**：后端通过 Mapper 接口（如 [**UserMapper.java**](air-combat-backend/src/main/java/com/aircombat/mapper/UserMapper.java)、[**RoomMapper.java**](air-combat-backend/src/main/java/com/aircombat/mapper/RoomMapper.java)、[**BattleRecordMapper.java**](air-combat-backend/src/main/java/com/aircombat/mapper/BattleRecordMapper.java) 等）定义 SQL 操作，XML 映射文件在 `resources/mapper/` 下编写具体 SQL。`application.yml` 中配置了 `map-underscore-to-camel-case: true`，自动完成数据库下划线字段到 Java 驼峰属性的转换。

**战报入库流程**：`tick()` 检测到胜负后 → `saveBattleRecord(runtime, snapshot)` 写入 `battle_records` 和 `battle_player_results` 两张表，使用 `AtomicBoolean recordSaved` 保证只写一次。对局结束后广播的 `BATTLE_FINISHED` 事件中已携带战报 ID、胜负方、时长、击杀等数据，前端可据此做战报展示。REST 接口 `GET /api/rooms/{id}/battle-history` 和 `GET /api/battles/my-history` 支持按房间或个人查询历史战报。

### 八、并发模型与线程池

后端并发模型是本次课程的重点，采用 **"单线程调度 + 双线程池执行"** 三层结构（[**ThreadPoolConfig.java**](air-combat-backend/src/main/java/com/aircombat/config/ThreadPoolConfig.java) 第 12–31 行）：

| 组件 | 线程数 | 队列 | 职责 |
|------|--------|------|------|
| `tickScheduler` | 单线程守护 | — | 按 `tick-rate`（120Hz）定时触发 `dispatchTicks()`，遍历 RUNNING 房间投递 tick 任务到 `gameTaskExecutor`。自身只做调度，不计算 |
| `gameTaskExecutor` | 核心4 / 最大8 | 200 | 执行每个房间的 `tick()` 方法。通过 `synchronized(runtime)` 保证同一房间串行，不同房间可以并行 |
| `calculationTaskExecutor` | 核心4 / 最大8 | 400 | 通过 `CompletableFuture.supplyAsync` 异步执行 AI 决策（`buildAiCommands`）和碰撞检测（`detectHits`、`scanRadarMarks`）。队列更大（400 vs 200），因为计算任务是批量涌入的 |

**为什么这样设计？** 核心思想是**计算与调度分离**：

1. `tickScheduler` 对延迟敏感，必须准时。如果让它直接做 AI 计算，一个慢 AI 就会拖慢所有房间的 tick 节拍。所以它只投递任务，超轻量。
2. `gameTaskExecutor` 执行 tick 本体。`synchronized(runtime)` 保证同一房间状态修改线性化——这意味着不需要分布式锁或细粒度加锁，一个房间的状态永远只被一个线程修改。
3. `calculationTaskExecutor` 处理 CPU 密集型子任务。AI 决策（`buildAiCommands` 要遍历所有 AI 战机）和碰撞检测（`detectHits` 要对每枚导弹找最近敌机）通过 `CompletableFuture.join()` 在 tick 内收敛结果。如果计算线程池繁忙，队列缓冲 400 个任务，避免直接拒绝。

另外还有一个细节：**pending 意图机制**。高频输入下（前端 60Hz 上行），同一个 tick 内可能收到多条 `MSG_PLAYER_INPUT`，后一条可能 `fire=false` 覆盖前一条的 `fire=true`，导致导弹发射被漏掉。所以在 `handleClientMessage` 中，`fire=true` 时不仅写 `latestInputs`，还写 `pendingMissileByFighter`；tick 消费时合并两者，保证"按钮按下就不会丢"。

### 九、Tick 循环 · 游戏机制

这是整个后端最核心的方法——[**OnlineGameService.java**](air-combat-backend/src/main/java/com/aircombat/service/OnlineGameService.java) 的 **`tick` 方法（第 349–608 行）**，每 tick 执行 11 步：

**1. AI 机头朝向**（`stepAiNoseForAiFighters`）：离线玩家的战机保持最后朝向；AI 战机的 nose 逐渐转向最近敌机，加上一定侧向偏移和正弦抖动，模拟"盘旋接近"的飞行行为。

**2. AI 决策**（`buildAiCommands` → `calculationTaskExecutor` 异步）：为每个 AI 战机生成 `InputCommand`。AI 逻辑（`createAiInput`）计算到最近敌机的导航向量、以侧向偏移逼近（模拟战术机动）、在距离 < 260 且机头对准时以概率发射导弹，距离 < 200 时概率投弹。概率值按 `tickRate` 缩放，确保不同 tick 频率下 AI 开火频率一致。

**3. AWACS 移动**：双方 KJ-500 预警机跟随己方存活友机的重心坐标，距离 > 80px 时以固定速度靠近，保持在大致对应半场。

**4. 移动执行**（`applyMove`）：根据 `InputCommand` 的 `moveX/moveY` 更新坐标与朝向。边界 clamp 在 50~3550 / 50~2110（即离世界边缘 50px）。

**5. 武器发射**：消费 `fire`/`fireBomb` + pending 意图 → 创建 `MissileRuntime`/`BombRuntime`。导弹如果指定了 `targetId` 则锁定，否则自动选最近敌机。如果目标在己方 AWACS 探测区内 → `homingActive = true`，启动追踪。

**6. 导弹步进**（`steerMissile`）：若 `homingActive` 且目标存活且在 AWACS 覆盖下 → 持续转向目标（角速度上限 `π × 2.8 rad/s`）；否则直飞。TTL 3.5s，出界则失效。注意这是通过 `isEnemyCoveredByFriendlyAwacs` 判断——只有 AWACS 提供探测，战斗机自身没有雷达。

**7. 炸弹步进**：匀速直线飞行，TTL 3s 到期或近距碰撞（`BOMB_PROXIMITY_DIST = 30`）触发 AOE 爆炸。爆炸对半径内所有敌机造成 `blastDamage`，并产生伤害飘字 `damagePopups`。

**8. 碰撞检测**：分两路异步到 `calculationTaskExecutor`——
- 导弹命中（`detectHits`）：每枚存活导弹找最近敌机，距离 ≤ 22 判命中，扣 `missileDamage` 并销毁导弹
- 战机互撞（`detectFighterCollisions`）：红蓝及同队两两检查，距离 < 30px 各扣 `maxHp × 50%`，同一对战对 60 tick（0.5s）冷却

**9. 雷达扫描**（`scanRadarMarks`）：仅 AWACS 单元提供探测，范围随 HP 线性缩放（最大 900）。每个目标只被首个覆盖它的 AWACS 标记，去重。

**10. 快照组装**（`toSnapshot`）：将 `fighters`、`missiles`（存活）、`bombs`（存活）、`radarMarks`、`damagePopups`、`redAlive`、`blueAlive` 组装为 `BattleSnapshot` record，通过 `broadcast` 下发 `MSG_BATTLE_STATUS`。

**11. 胜负判定**：排除 AWACS 后，某方全灭 → `RED_WIN` / `BLUE_WIN`；同时全灭 → `DRAW`。广播 `BATTLE_FINISHED`，调用 `saveBattleRecord` 入库战报。

**机型属性**：后端 `MODEL_STATS` Map 存储了 4 种机型 + F-16（蓝方可用）的属性——J-20（隐身高速）、J-16（重火力）、J-10C（均衡）、J-25（极速轻甲）。蓝方 AI 属性统一 ×0.7 弱化。

## 附录 · 临场提问（简答备忘）

| 提问 | 可答要点 |
|------|----------|
| 为什么选 Spring Boot 3？ | 课程要求 Spring Boot；3.x 支持 Java 17 record、虚拟线程等新特性；WebSocket 集成简单 |
| 为什么选 MyBatis 而不是 JPA？ | MyBatis SQL 可控性更强，手写 SQL 便于调优和排查；课程上已学 MyBatis |
| 为什么选 120 tick/s？ | 可配（`application.yml`），120 在流畅度与 CPU 开销间平衡；实际 tick 间隔 `Math.max(20, 1000/tickRate)` 保证不低于 20ms |
| 如何保证多人同时操作不冲突？ | `synchronized(runtime)` 同房间串行；`latestInputs` 只保留最新输入，pending 意图兜底开火不丢失 |
| 断线了怎么办？ | `onlineUsers` 移除该用户 → 其战机的 `controlType` 自动切为 AI → `buildAiCommands` 接管 |
| 网络协议为什么用 JSON？ | 可读易调试、与 WebSocket 文本帧天然兼容；`INetworkProtocol` 接口解耦后可以换二进制（如 Protobuf） |
| 单点登录怎么实现的？ | `users.auth_revision` 字段，每次登录 +1；JWT 内嵌 `arv` claim；WebSocket 每 20 条消息或 2s 节流校验——不匹配则踢下线（4001） |
| 和单机的线程池概念怎么对应？ | 单机 `rAF` 主线程；联机 `gameTaskExecutor` = 游戏主循环线程池，`calculationTaskExecutor` = 计算线程池，体现计算/调度分离 |
| Canvas 为什么不用 WebGL？ | 2D 顶视战场不需要 3D 渲染；Canvas 2D 足够且更简单；离屏缓冲 + 脏矩形已满足性能要求 |
| 前端状态为什么不用 Pinia？ | 状态结构简单（auth + room），Vue 3 的 `ref`/`shallowRef` 即够用，不引入额外依赖 |
| 为什么不是 exe 而是 Web？ | SPA + Canvas 跨平台零安装；若要 exe 可用 Electron/Tauri 封装 |
